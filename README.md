# Mini NPU Simulator (MAC 연산 기반 패턴 인식기)

외부 수치 연산 라이브러리(`NumPy` 등) 없이 **순수 Python 표준 라이브러리(`json`, `time`)만** 사용하여 NPU(Neural Processing Unit)의 핵심 연산인 **MAC(Multiply-Accumulate, 곱셈-누산)** 을 구현한 콘솔 애플리케이션입니다.

입력 패턴과 필터 행렬 간의 유사도 점수를 계산하여 패턴(`Cross` / `X`)을 판정하고, 행렬 크기(\(N \times N\))가 커질 때 연산량과 실행 시간이 어떻게 변하는지(\(O(N^2)\)) 직접 확인해 볼 수 있습니다. 입력 크기 N행 N열(\(N \times N\))에 따른 연산 성능 및 시간 복잡도를 분석합니다.

---

### 시작 전 핵심 4가지 개념

1. **MAC (Multiply-Accumulate, 곱셈 뒤 더하기)**
   - 두 행렬의 **같은 위치 `(i, j)`에 있는 숫자끼리 곱한 뒤, 그 결과를 계속 더하는 연산**입니다(`score += matrix_a[i][j] * matrix_b[i][j]`).
   - 패턴 인식에서는 "필터(찾고 싶은 모양)"와 "입력 패턴"이 겹치는 위치에 큰 값이 많을수록 점수가 높게 나옵니다.
2. **필터(Filter)와 패턴(Pattern)**
   - **필터**: `'+'` 모양(`Cross`)이나 `'X'` 모양처럼 특정 특징을 찾기 위한 가중치 행렬입니다.
   - **패턴**: 판별 대상이 되는 2차원 숫자 격자(행렬)입니다. 두 필터 중 더 높은 점수를 얻은 쪽으로 패턴을 분류합니다.
3. **부동소수점 허용오차(\(\epsilon = 10^{-9}\))와 `UNDECIDED`**
   - 컴퓨터의 실수(`float`) 연산에는 아주 작은 오차가 생길 수 있습니다. 두 점수의 차이가 `1e-9`(`0.000000001`)보다 작으면 사실상 **동점**으로 보고 어느 한쪽으로 치우치지 않게 `"UNDECIDED"`(판정 불가)로 처리합니다.
4. **시간 복잡도 \(O(N^2)\)**
   - 가로 \(N\), 세로 \(N\) 크기의 행렬 칸을 하나씩 모두 살펴보려면 이중 반복문(`for i in range(size): for j in range(size):`)이 필요하며, 총 **\(N \times N = N^2\)번** 연산합니다. 행렬 한 변의 길이가 늘어나면 연산 횟수는 제곱으로 늘어납니다.

  * 입력이 끝나면 `calculate_mac()`을 10회 반복 실행해 A/B 점수, 10회 평균 연산 시간(ms), 연산 횟수(9), 판정 결과를 출력합니다.
  * 숫자가 아닌 값을 입력하거나 한 줄에 3개가 아닌 개수를 입력하면 에러 메시지를 띄우고 해당 줄을 다시 입력받습니다.

  * 파일이 없거나(`FileNotFoundError`) JSON 문법이 깨진 경우(`json.JSONDecodeError`) 안내 메시지를 출력하고 안전하게 종료합니다.
  * 개별 테스트 케이스의 스키마나 크기가 잘못되더라도 전체 프로그램이 멈추지 않고 해당 케이스만 `FAIL`로 기록한 뒤 다음 케이스를 이어서 진행합니다.

### 코드 구조 및 주요 함수 역할

`main.py`는 크게 **공통 함수**, **모드 1**, **모드 2**, **메인 메뉴**로 나뉩니다.

* **`calculate_mac(matrix_a, matrix_b)`**: 이중 `for`문으로 두 $N \times N$ 행렬의 원소별 곱을 누적합(`score`)으로 계산합니다.
* **`judge_pattern(score_a, score_b, label_a="A", label_b="B")`**: `abs(score_a - score_b) < 1e-9`이면 `"UNDECIDED"`, 크면 더 높은 점수 쪽의 라벨을 반환합니다.
* **`is_valid_matrix(matrix, expected_size)`**: 데이터가 리스트 형태인지, 전체 행 개수가 `expected_size`인지, 모든 행의 길이가 `expected_size`인지 확인합니다.
* **`get_matrix_input(size, name)`**: 콘솔에서 `size × size` 실수(`float`) 행렬을 안전하게 입력받습니다.
* **`mode_user_input()`**: `3×3` 필터 A/B와 패턴을 입력받아 MAC 점수와 연산 시간을 출력합니다.
* **`mode_json_analysis()`**: `data.json`의 필터·패턴을 검증 및 분석하고, 크기별 성능 표와 최종 합격/불합격 요약을 출력합니다.

### 함수 상세 설명

* **MAC(Multiply-Accumulate) 연산 구현**
  * NumPy 등 벡터화 라이브러리를 사용하지 않고, 이중 `for` 반복문을 통해 입력 행렬과 필터 행렬의 같은 위치 $(i, j)$ 원소를 곱한 뒤 누적합(`score += matrix_a[i][j] * matrix_b[i][j]`)을 계산하는 방식으로 직접 구현했습니다.

* **라벨 정규화(표준화) 방식**
  * `data.json` 내부의 서로 다른 라벨 표기를 통일하기 위해 프로그램 내부 표준 라벨로 `Cross`와 `X`를 사용합니다.
  * `expected` 값의 `'+'` $\rightarrow$ `Cross`, `'x'` $\rightarrow$ `X`로 매핑하고, `filters` 키의 `'cross'` $\rightarrow$ `Cross`, `'x'` $\rightarrow$ `X`로 정규화하여 일관된 기준으로 비교 및 출력합니다.

* **부동소수점 및 동점 처리 정책 ($\epsilon$)**
  * 실수(`float`) 곱셈·덧셈 과정에서 발생할 수 있는 미세한 부동소수점 오차를 고려하여 허용오차 $\epsilon = 10^{-9}$ (`1e-9`) 기준을 적용했습니다.
  * 두 필터 점수의 차이 `abs(score_a - score_b) < 1e-9`인 경우 어느 한쪽으로 판정하지 않고 `UNDECIDED`(판정 불가)를 반환합니다.

* **스키마 및 입력 검증**
  * 모드 1에서는 행·열 개수 불일치 및 숫자 변환(`float`) 오류 시 안내 문구를 출력하고 재입력을 유도합니다.
  * 모드 2에서는 패턴 키에서 추출한 크기 $N$과 실제 필터·패턴 행렬의 크기($N \times N$)가 일치하는지 검증하여, 불일치 시 프로그램이 비정상 종료되지 않고 해당 케이스만 `FAIL` 처리합니다.

## 3. 결과 리포트

### 3.1 테스트 실행 결과 요약 (`data.json`)
* **총 테스트**: 6개
* **통과 (PASS)**: 3개 (`size_5_2`, `size_13_1`, `size_25_2`)
* **실패 (FAIL)**: 3개 (`size_5_1`, `size_13_2`, `size_25_1`)

### 3.2 FAIL 케이스 원인 분석
실패한 3개 케이스(`size_5_1`, `size_13_2`, `size_25_1`)의 원인을 **데이터/스키마 문제**, **로직 문제**, **수치 비교 정책**으로 분리하여 진단한 결과는 다음과 같습니다.

1. **데이터/스키마 및 연산 로직 점검 (정상)**
   * 라벨 정규화(`+` $\rightarrow$ `Cross`, `x` $\rightarrow$ `X`)와 행렬 크기 검증을 모두 정상 통과했으며, MAC 연산 누적합 계산에도 오류가 없었습니다.
2. **수치 비교 정책(동점 규칙)에 의한 판정 불가 (`UNDECIDED`)**
   * **실패 케이스별 실제 점수 계산 결과**
     * `size_5_1` (기댓값 `X`): `Cross` 필터는 중앙 1칸만 겹쳐 `0.9 × 1.0 = 0.90`, `X` 필터는 대각선 9칸이 겹쳐 `0.1 × 1.0 × 9 = 0.90`으로 두 점수가 동일합니다.
     * `size_13_2` (기댓값 `Cross`): `Cross` 필터는 십자 25칸이 겹쳐 `0.3 × 1.0 × 25 = 7.50`, `X` 필터는 중앙 1칸이 겹쳐 `7.5 × 1.0 = 7.50`으로 두 점수가 동일합니다.
     * `size_25_1` (기댓값 `X`): `Cross` 필터는 중앙 1칸만 겹쳐 `4.9 × 1.0 = 4.90`, `X` 필터는 대각선 49칸이 겹쳐 `0.1 × 1.0 × 49 = 4.90`으로 두 점수가 동일합니다.
   * **분석 결론**: 세 케이스 모두 코드 오류가 아니라, 두 필터의 MAC 점수가 정확히 같아지도록 설계된 경계 테스트 데이터입니다. 본 프로그램의 허용오차 비교 정책(`|score_a - score_b| < 1e-9`)이 정상 작동하여 `UNDECIDED`로 판정되었고, 기댓값(`Cross` 또는 `X`)과 일치하지 않으므로 최종 리포트에서 `FAIL`로 분류되었습니다.

### 3.3 성능 표 해석 및 시간 복잡도 $O(N^2)$ 근거
I/O(파일 읽기 및 콘솔 출력) 시간을 제외하고 순수 `calculate_mac()` 함수 호출 구간만 10회 반복 측정한 평균 실행 시간은 다음과 같습니다.

| 행렬 크기 ($N \times N$) | 연산 횟수 ($N^2$) | 기준 크기(5×5) 대비 연산량 배율 | 평균 연산 시간 (ms) |
| :---: | :---: | :---: | :---: |
| **3×3** | 9 | 0.36배 | 0.020 |
| **5×5** | 25 | 1.00배 | 0.028 |
| **13×13** | 169 | 6.76배 | 0.196 |
| **25×25** | 625 | 25.00배 | 0.691 |

* **$O(N^2)$ 시간 복잡도 근거**
  * `calculate_mac()`은 가로 $N$, 세로 $N$ 크기의 2차원 배열 모든 원소를 한 번씩 방문하기 위해 `N`번 반복하는 바깥쪽 루프와 `N`번 반복하는 안쪽 루프(이중 반복문)로 구성되어 있습니다.
  * 따라서 입력 크기 $N$에 대해 총 곱셈-누산 연산 횟수는 정확히 $N \times N = N^2$번 수행됩니다.
  * 실측 데이터에서도 행렬의 한 변 길이 $N$이 `5`에서 `25`로 **5배** 커질 때, 연산 횟수는 $25$회에서 $625$회로 **$5^2 = 25$배** 증가하며, 평균 연산 시간 역시 `0.028 ms`에서 `0.691 ms`로 약 **24.7배**(비례 수준) 증가합니다. 이를 통해 알고리즘의 시간 복잡도가 $O(N^2)$임을 이론과 실측 결과 모두로 확인할 수 있습니다.

## 4. 과제 목표 및 핵심 개념 정리

### 1) MAC 연산과 AI에서의 중요성
**MAC** 연산은 **Multiply-Accumulate(곱해서 누적하기)**의 줄임말로, 두 숫자를 곱한 뒤 그 결과를 기존 값에 계속 더하는 계산을 뜻합니다.

$$\text{누적값} \leftarrow \text{누적값} + (A \times B)$$

인공지능(특히 딥러닝·신경망)이 데이터를 보고 판단하거나 글·이미지를 만들어 낼 때는 입력값과 가중치(중요도)를 곱한 뒤 모두 더하는 계산을 수백만~수천억 번 반복합니다.

* **신경망 계산의 핵심**: AI 모델이 "이 사진이 고양이일 확률"이나 "다음에 올 단어"를 계산할 때, 각 특징(입력값)에 중요도(가중치)를 곱해 합산하는 과정이 곧 행렬 곱셈이며, 그 속을 채우는 기본 단위가 MAC 연산입니다.
* **하드웨어 성능의 기준**: AI 칩이나 GPU, NPU의 연산 성능을 비교할 때 MAC 연산을 1초에 얼마나 많이 처리할 수 있는지가 핵심 기준이 됩니다. 곱셈과 덧셈을 따로 처리하기보다 한 번에 이어서 처리하도록 회로를 설계하면 속도와 전력 효율이 크게 좋아집니다.
* **모델 크기와 직결**: AI 모델의 규모(파라미터·가중치)가 커질수록 필요한 MAC 연산 횟수도 함께 늘어나므로, 연산량을 줄이면서도 정확도를 지키는 경량화·최적화 기법이 중요해집니다.

> **요약**: MAC 연산은 "곱하고 더해서 쌓는" 아주 단순한 계산이지만, AI가 수천억 번 되풀이하는 핵심 계산 조각이기 때문에 AI의 속도와 효율을 좌우합니다.

### 2) 입력 패턴과 필터를 곱하고 더해서 유사도(점수)를 계산하는 원리
* 2차원 패턴과 필터(찾고 싶은 특징이나 기준이 담긴 숫자 격자)를 겹쳐 놓고, 같은 위치의 숫자끼리 곱한 뒤 모두 더해 점수를 내는 과정을 통해 두 격자가 얼마나 잘 맞아 떨어지는지(특징이 얼마나 강하게 나타나는지)를 숫자로 환산합니다.

### 3) `data.json`의 키·라벨 규칙 해석과 내부 표준화(정규화) 이유
* 외부 파일(`data.json`)에서 어떤 이름(키, 라벨)으로 데이터가 들어오는지 규칙을 파악하고, 프로그램 안에서 쓰기 편하게 통일된 형태(표준화·정규화)로 바꾸는 이유는 외부 데이터의 대소문자나 표기 방식이 제각각일 수 있기 때문입니다.
* 프로그램 내부에서 기준을 하나로 맞추면 뒤따르는 계산이나 판정 로직이 꼬이지 않고 깔끔하게 동작합니다.

### 4) 부동소수점 오차의 영향과 허용오차(`epsilon`) 기반 비교 정책의 필요성
컴퓨터가 소수를 다룰 때 생기는 미세한 계산 오차(부동소수점 오차) 때문에 `==` 같은 엄격한 비교를 하면 "같아야 하는데 다르다"고 잘못 판정될 수 있습니다. 예를 들어 수학적으로는 `0.3`이어야 할 계산 결과가 컴퓨터에서는 `0.29999999999999993`처럼 나올 수 있습니다.

* **왜 이런 숫자가 나오나? (원인)**
  * 컴퓨터는 사람이 쓰는 10진수가 아니라 **2진수**로 소수를 저장하고 계산합니다. `0.1 + 0.2`처럼 수학적으로는 딱 `0.3`이 떨어져야 할 계산도, 2진수로 표현하는 과정에서 끝없이 이어지는 소수를 자르다 보니 `0.30000000000000004`나 `0.29999999999999993`처럼 미세한 오차가 생길 수 있습니다.
* **그냥 `==`로 비교하면 어떤 문제가 생기나? (영향)**
  * 두 필터의 점수를 비교할 때, 논리적으로는 같은 점수인데 한쪽이 `0.3`이고 다른 쪽이 `0.29999999999999993`로 계산될 수 있습니다. 이때 `==`나 `!=`처럼 **완전히 똑같은지만 따지는 엄격한 비교**를 하면, 실제로는 동점인데 **"다르다"고 잘못 판정**하게 됩니다.
* **허용오차(`epsilon`)로 어떻게 해결하나? (대책)**
  * 두 값의 차이가 **`epsilon`(예: `1e-9` 같은 아주 작은 허용 한계)**보다 작으면 **"오차 범위 안이니 사실상 같다"**고 판단하도록 기준을 둡니다. 이 코드에서도 두 필터 점수의 차이가 `1e-9` 미만이면 한쪽으로 무리하게 판정하지 않고 **`UNDECIDED`(판정 불가)**로 처리해 비교의 안정성을 높였습니다.

> **요약**: 수학적으로는 `0.3`이어야 할 값이 컴퓨터의 부동소수점 연산 때문에 `0.29999999999999993`처럼 미세하게 어긋날 수 있습니다. 이때 `==`로 엄격히 비교하면 같은 값인데도 다르다고 판정되므로, 차이가 `epsilon` 이내면 같다고 보는 허용오차 기준을 두어 판정 오류를 막았습니다.

### 5) 크기별 연산 시간 측정과 시간 복잡도 $O(N^2)$의 근거
* 패턴 크기가 커질 때(예: $3\times 3 \rightarrow 5\times 5 \rightarrow 13\times 13 \rightarrow 25\times 25$) 가로·세로가 $N \times N$인 2차원 영역을 훑으며 계산하면 전체 칸 수가 $N^2$개이기 때문에, 크기가 커질수록 연산 횟수도 제곱에 비례해 빠르게 늘어납니다.

### 6) 실패 케이스 발생 시 원인 분리 진단 및 개선 (데이터/스키마 vs 로직 vs 수치 비교)
테스트나 실행에서 원하는 결과가 안 나왔을 때 막연히 헤매지 않고, 원인을 세 가지로 분리해 진단하고 개선합니다.

1. **데이터/스키마 문제**: 입력 파일 구조, 키 이름, 타입, 형식 자체가 잘못되었는가?
2. **로직 문제**: 곱하고 더하는 계산 순서, 인덱스, 조건문 등 코드 흐름에 버그가 있는가?
3. **수치 비교 문제**: 계산은 맞았는데 소수점 오차나 `epsilon` 기준 때문에 통과/실패 판정이 어긋났는가?

> **핵심 정리**: 단순히 "직접 계산하고 비교하는 코드를 만드는 것"에서 끝나지 않고, **왜 이렇게 계산하는지(원리)**, **데이터와 숫자를 어떻게 안전하게 다루는지(정규화·오차)**, **커질 때 얼마나 느려지는지(복잡도)**, **틀렸을 때 어디를 고쳐야 하는지(디버깅 관점)**까지 스스로 설명할 수 있도록 구현했습니다.
